# i18n for PhanteonNext — Design Spec

**Date:** 2026-07-10 (revised 2026-07-16: t-API interpolation/plural/rich-text contract, date formatting, static rendering, out-of-`src/app` files, locale-detection redirects, Cyrillic font subset, localized 404, permanent Cyrillic check)
**Status:** Approved design, pending implementation plan

## Goal

Internationalize all static (hardcoded) user-facing content in the app. Ship two complete locales: Ukrainian (`uk`, default — the current source language) and English (`en`). Single delivery: infrastructure plus full migration of all ~103 files containing user-facing text (99 under `src/app`, plus `src/hooks/TradingBots/useAlgonixSession.ts` and module-level Zod schemas in `src/api/Auth/types.ts`), in one pass.

## Decisions (approved)

| Decision | Choice |
|---|---|
| Locales | `uk` (default) + `en` |
| Engine | `next-intl` with a typed house-pattern wrapper |
| URL strategy | Locale in path, `localePrefix: 'as-needed'` — Ukrainian keeps existing unprefixed URLs (`/About`), English under `/en/...` |
| English copy | Drafted by Claude during extraction, reviewed by the team in `en.json` |
| Delivery | Everything in one pass (no phased rollout) |

`as-needed` prefixing means zero broken bookmarks, shared links, indexed pages, or external payment-callback URLs, and no mass redirects.

## Current state (from codebase scan)

- Next.js 16 App Router, React 19; 56% of components are client (`"use client"` in 77 files). Screener, Auth, and most of myCabinet are fully client.
- All UI text is hardcoded Ukrainian; ~99 of 136 files under `src/app` contain user-facing text, 42+ heavily.
- Zero existing i18n: no library, no middleware, no locale routes, no translation files, no switcher.
- Known defects fixed by this work: `<html lang='en'>` on a Ukrainian UI; hardcoded English metadata with `uk-UA` OpenGraph locale; Montserrat loaded with `subsets: ['latin']` only (`src/app/layout.tsx`) — the Ukrainian UI renders in a fallback font today; fix by adding `'cyrillic'` to the subsets.
- 26 files import `next/link`; 32 import `next/navigation`; 3 server-side `redirect()` calls (`payments/layout.tsx`, `dashboard/page.tsx`, `myCabinet/layout.tsx`).
- Zod schemas with Ukrainian messages exist inside components (Login, Register, forgotPassword, tradingBots forms) and at module level in `src/api/Auth/types.ts` (6 schemas: Profile, ChangePassword, ForgotPassword, SetNewPassword, ChangeLogin, DeleteAccount). Correction from the original scan: `src/api/TradingBots/schemas.ts` is wire-contract validation only — no user-facing text, stays untouched.
- Login component maps English API errors to hardcoded Ukrainian strings.
- User-facing Ukrainian text also exists **outside `src/app`**: `src/hooks/TradingBots/useAlgonixSession.ts:76-82` creates `Error` objects with Ukrainian messages that render in the UI. (Other Cyrillic hits outside `src/app` are code comments — out of scope.)
- ~8 call sites hardcode `toLocaleDateString('uk-UA')` / `toLocaleTimeString('uk-UA')` (Blog, LatestWebinar, cabinet webinars/certificates/subscriptions) — dates would stay Ukrainian in the English locale without migration.
- `next.config.ts` has a `/tron-proxy/:path*` rewrite that the middleware matcher must exclude alongside `/api` and `/screener-proxy`.

## Architecture

### Routing

- All pages and layouts move from `src/app/*` to `src/app/[locale]/*`. `src/app/api/` and `src/app/screener-proxy/` remain at `src/app/` (route handlers, not localized).
- New `src/middleware.ts` using next-intl middleware: locale resolution order is `NEXT_LOCALE` cookie → `Accept-Language` header → default `uk`. The user's switcher choice persists via the `NEXT_LOCALE` cookie. Matcher excludes `/api`, `/screener-proxy`, `/tron-proxy` (existing rewrite), `_next`, and static-file paths.
- **Redirect nuance (explicit):** with `as-needed` + detection enabled, a visitor whose cookie or `Accept-Language` resolves to `en` and who opens an unprefixed URL (`/About`, `/payment-result?...`) gets a 307 to `/en/...` (query string preserved by next-intl). This is accepted behavior: Googlebot sends no `Accept-Language`, so unprefixed pages index as Ukrainian; hreflang alternates (see SEO) cover the rest. Payment callbacks land correctly either way — verified in DoD. We keep detection enabled; if en-redirects on unprefixed URLs ever become a problem, the documented fallback is `localeDetection: false` (unprefixed always serves `uk`; switcher-only locale changes).
- **Static rendering preserved:** `generateStaticParams` returns both locales, and `setRequestLocale(locale)` is called at the top of the locale layout and of every statically-renderable page/layout before any next-intl call. Without this, next-intl forces every page under `[locale]` into dynamic rendering — a silent perf/SEO regression for About, privacy, home, etc.
- New `src/i18n/routing.ts` (`defineRouting`: locales `['uk','en']`, defaultLocale `'uk'`, localePrefix `'as-needed'`) and `src/i18n/request.ts` (message loading per request).
- New `src/i18n/navigation.ts` via `createNavigation`, exporting locale-aware `Link`, `useRouter`, `usePathname`, `redirect`. Every current import of `next/link` (26 files) and `next/navigation` routing APIs (32 files) switches to these. Existing path strings (`router.push('/login')`, `redirect('/myCabinet/screener')`) remain unchanged but become locale-preserving.
- `src/app/[locale]/layout.tsx` renders `<html lang={locale}>` and wraps children in `NextIntlClientProvider` (inside the existing `QueryProvider`).

### Translation infrastructure (house pattern)

- `src/i18n/messages/uk.json` and `src/i18n/messages/en.json` — one file per locale, namespaced by feature area: `common`, `nav`, `auth`, `home`, `about`, `blog`, `contacts`, `webinars`, `notFound`, `paywall`, `payments`, `cabinet.personalData`, `cabinet.subscriptions`, `cabinet.certificates`, `cabinet.settings`, `cabinet.webinars`, `cabinet.studyPlatform`, `screener`, `tradingBots`, `aiAgent`, `tradingChat`, `errors`, `validation`, `meta`. Keys are descriptive camelCase (`saveChanges`, `noActiveSubscriptions`).
- `src/i18n/t-keys.ts` — typed key tree **auto-generated from `uk.json`** by `scripts/generate-t-keys.js`. Never hand-edited; regenerated whenever messages change, so a stale key is a TypeScript compile error.
- `src/lib/contexts/translations/`:
  - `translations-context.tsx` — `useCustomTranslations(TKeys.cabinet.subscriptions)`: client hook wrapping next-intl `useTranslations`, returning an object-style `t` (`t.monthlyPlan`).
  - `translations-server.ts` — `getCustomTranslations(TKeys.…)`: async server twin wrapping `getTranslations`, for server components and `generateMetadata`.
- **`t` leaf contract (three message kinds).** The generator classifies every message in `uk.json` at build time, and the runtime proxy mirrors the same classification, so types and behavior always agree:
  - **Plain** (no ICU braces, no tags): `t.saveChanges` is a `string`.
  - **Parameterized** (contains ICU arguments like `{count}`, including `{x, plural, …}` / `{x, select, …}`): the leaf is a function — `t.minChars({ count: 8 })` → `string`. Interpolated template literals in the codebase (`` `Мінімум ${minLen[1]} символів` ``, `` `Помилка: ${errorDetail}` ``) migrate to this form.
  - **Rich** (contains tags like `<link>…</link>`): the leaf is a function taking tag renderers — `t.consent({ link: (chunks) => <a href='…'>{chunks}</a> })` → `ReactNode`, wrapping next-intl `t.rich`. Used for messages with embedded markup (login consent text, privacy-page paragraphs with links).
- **Plurals are ICU, mandatory for counts.** Ukrainian has three plural categories (`one`/`few`/`many`, plus `other` for fractions). Any count-based message must use ICU plural syntax in both locale files, e.g. `{count, plural, one {# сертифікат} few {# сертифікати} many {# сертифікатів} other {# сертифіката}}`. Never compose plurals by string concatenation.
- `scripts/validate-i18n.mjs` + `npm run validate-i18n` — fails on any key missing or extra between `uk.json` and `en.json`; also runs t-keys regeneration and fails if `t-keys.ts` is stale.
- **Permanent Cyrillic check** (`npm run validate-i18n:full`): the same script with `--cyrillic` also scans `src/**/*.{ts,tsx}` (excluding `src/i18n/messages/`, excluding comments) for Cyrillic characters, with a documented allowlist file. During migration the base `validate-i18n` runs per task; from the final task onward `validate-i18n:full` is the CI/pre-merge gate — the DoD grep becomes a permanent regression guard, not a one-time check.
- Scripts are plain Node (v22, `node:test` for their tests — no new test-framework dependency).

### Usage rules (enforced during migration and after)

1. Always `TKeys.x.y`, never string paths.
2. No fallback values (`t.key || '…'` is forbidden) — validation guarantees presence.
3. No passing translated strings as props — each component calls the hook itself.
4. New keys always added to both locale files; `validate-i18n` run afterwards.

## Content migration

- **Client components** (77 files): replace each hardcoded string with `t.someKey` via `useCustomTranslations(TKeys.<namespace>)`. Namespace derives from file location (`myCabinet/subscriptions/page.tsx` → `TKeys.cabinet.subscriptions`; shared components → `common`/`nav`).
- **Server components/pages** (About, privacy, not-found, layouts, home): same via `getCustomTranslations`.
- **Zod schemas with user-facing messages**: converted to factory functions — e.g. `createLoginSchema(t)` — invoked inside the consuming component with the hook's `t` (under the `validation` namespace). Module-level schemas without user-facing text stay untouched.
- **API-error mapping** (Login): English API error → key under `errors.*`, resolved through the hook, so messages follow the active locale.
- **User-facing errors outside `src/app`**: `useAlgonixSession.ts` gets the same treatment — its Ukrainian `Error` messages become keys under `errors.*`, resolved where the error is rendered (the hook returns an error key or code; the consuming component translates it).
- **Date/time formatting**: the ~8 `toLocaleDateString('uk-UA')` / `toLocaleTimeString('uk-UA')` call sites (Blog list/comments, LatestWebinar, cabinet webinars/certificates/subscriptions) switch to next-intl `useFormatter` (client) / `getFormatter` (server) so month names and formats follow the active locale. **Deliberate exception:** numeric price/balance formatting stays `en-US` (`src/lib/screener/format.ts`, `BalanceCard.tsx`) — crypto prices conventionally use dot-decimal in both locales.
- **English copy**: drafted during extraction, matching the existing marketing voice (trading/crypto product). Review happens in `en.json` as a single-file sweep.

### Out of scope

- Dynamic backend content: blog posts, webinar data, study-platform content, API payloads.
- Alt text on purely decorative images; console/log strings; code comments.
- Any locale beyond `uk`/`en` (structure makes adding one = one JSON file + config entry).

## SEO and metadata

- Root `metadata` becomes `generateMetadata` in `src/app/[locale]/layout.tsx`: localized title/description from the `meta` namespace, `openGraph.locale` `uk_UA`/`en_US`, and `alternates.languages` hreflang entries.
- Pages with their own metadata follow the same pattern. `Blog/[slug]`'s existing `generateMetadata` gets locale threading; the post content itself stays whatever the backend returns.

## Language switcher

- Compact UK/EN toggle in the desktop Header and in the mobile Drawer.
- Implemented with the locale-aware navigation wrappers: switching locale keeps the current pathname. Persistence via the `NEXT_LOCALE` cookie (written by middleware).

## Error handling

- Missing message key in dev: loud next-intl console error.
- Locale parity is guaranteed pre-merge by `validate-i18n`.
- Unknown locale in URL (e.g. `/de/About`): middleware treats it as a pathname under the default locale → standard 404 via `notFound()` in the locale layout when `params.locale` is not in the configured list.
- **Localized 404 requires a catch-all**: the translated not-found page lives at `src/app/[locale]/not-found.tsx`, and unmatched paths reach it through `src/app/[locale]/[...rest]/page.tsx` that calls `notFound()` — a root `not-found.tsx` has no locale context and can't be translated.
- The legacy `src/app/404page/` route and `not-found.tsx` are reconciled during migration: one translated not-found implementation under `[locale]`, the redundant one removed.

## Verification / definition of done

1. `yarn build` passes, and About/privacy/home still appear as static (`○`/`●`, not `ƒ`) in the build output for both locales.
2. `npm run validate-i18n:full` green (locale parity + fresh `t-keys.ts` + no Cyrillic in `src` outside `i18n/messages` and the allowlist). This script stays as the permanent CI/pre-merge gate after delivery.
3. `node --test scripts/` green (generator + validator unit tests).
4. Manual smoke in both locales: home → login → myCabinet (subscriptions, screener, tradingBots) → About → Blog; switcher toggles locale and keeps the path; `/About` serves Ukrainian without a prefix; `/en/About` serves English; cookie persists the choice across navigation; `/api/*`, `/screener-proxy/*`, `/tron-proxy/*` unaffected; dates on Blog/webinars/subscriptions render localized month names per locale; a parameterized message (e.g. password min-length) and a plural message render correctly in both locales.
5. Payment-result/paywall redirect flows work with unprefixed URLs (external callbacks unchanged), **including** with an `en` `NEXT_LOCALE` cookie set — the 307 to `/en/payment-result` must preserve the query string.
6. Localized 404: unknown path shows the translated not-found page in both locales; `/de/About` returns 404.
